# Dev Journal — July 1, 2026

Today I extended the Memory Peg System frontend to dynamically update as time passes, rather than showing a static snapshot from page load. The core problem was simple: the app needed to display the correct 15-minute time character as each quadrant boundary passed (:00, :15, :30, :45). The solution I landed on was a chained `setTimeout` strategy — on page load, calculate the exact milliseconds until the next boundary, fire once, update the UI, then immediately arm the next timer. This means the browser wakes up at most 4 times per hour rather than polling constantly. I also added `prev` and `next` time characters to the banner so the user can see surrounding context while learning the system, which required modifying the backend's `buildCharacterResponse` to compute `pegIndex ± 1` with wraparound and return all three in a single API call.

The bigger headaches came from deployment. Mobile Safari on iPhone throttles or kills `setTimeout` timers whenever a tab is backgrounded or the screen locks — a platform-level restriction that silently breaks the feature. The fix was a `visibilitychange` listener that immediately re-fetches the correct character whenever the tab comes back into focus, effectively catching up on any missed boundary. On the Raspberry Pi Zero side, `pm2 restart` turned out to be unreliable — it acknowledged the command but the old Node.js process (started hours earlier) kept living on port 3000 and continued serving the old API response. Meanwhile the updated file was sitting correctly on disk the whole time, which made the bug particularly confusing to diagnose.

The resolution was to force-kill the stale process by PID (`kill 9303`), letting pm2 auto-respawn it from the updated file. Going forward, `pm2 reload` is the preferred deploy command over `pm2 restart` since it does a graceful in-place replacement that's more reliable on constrained hardware. The whole debugging chain — checking byte size of API responses, running `node -e` directly to test the file, `ps aux` to expose the zombie process, cross-referencing start times — ended up being a solid mental model for any future "why is my deployed app serving old code" situation.
